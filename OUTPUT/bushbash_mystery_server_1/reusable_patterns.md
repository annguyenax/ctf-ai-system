# Pattern — Rust/prost protobuf reversed via DWARF, canonical-default rejection

1. `checksec` first — Rust CTF binaries often keep DWARF even "unstripped" isn't
   obviously flagged; `readelf --debug-dump=info` then gives exact struct/enum
   layouts (way better than guessing from mangled `nm` symbols).
2. For `prost`-based wire protocols: `objdump -d` the `Message::encode_raw` and
   `Msg::encode` oneof-dispatch functions — the immediate value loaded before each
   `prost::encoding::*::encode` call is the literal protobuf field number/tag.
3. Validate any hypothesized framing by replaying the CLI's own generated bytes
   against the live server first, before hand-crafting new message types.
4. If a hand-crafted "empty"/zero-value field gets a generic decode error while
   normal non-default fields work fine: suspect a canonical-encoding /
   anti-tampering check that rejects explicitly-encoded default values (protobuf
   default should be omitted, not explicitly written). Fix by padding the field
   with non-empty junk content — the value itself is often not semantically
   checked, only its non-defaultness.
5. A CLI subcommand that panics with "not yet implemented" is often a deliberate
   stub — the intended solve is to hand-craft the wire bytes for that variant
   yourself, not to find a different subcommand.
6. An unused oneof/field variant (not exposed by any CLI subcommand) is a strong
   signal for a chained/harder follow-up challenge.
