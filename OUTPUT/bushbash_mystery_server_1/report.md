# Report — bushbash_mystery_server_1

## Goal

Reverse a Rust `client` binary generating protobuf messages for a custom TCP
protocol, then read the flag from `nc 34.40.133.67 6767`.

## Enumeration

- `checksec`: PIE, Full RELRO, NX, no canary, not stripped, **DWARF debug info present**.
- `readelf --debug-dump=info` → exact struct/enum layout for CLI `Operation` enum and
  `prost` wire types (`Echo`, `StoreMessage`, `ReadMessage`, `ReadFlag`,
  `ReadMultipleMessages`).
- `objdump -d` on `Msg::encode` dispatch + each `encode_raw` → literal field-number
  tags: 1=Echo(string), 2=StoreMessage(msg), 3=ReadMessage(uint32), 4=ReadFlag(empty
  msg), 5=ReadMultipleMessages(msg, unused by CLI → belongs to "mystery server II").
- Framing recovered empirically by replaying client-generated bytes at the live
  server: `[1-byte length][protobuf bytes][trailing 0x00]`, length = payload+NUL.
- `./client readflag` panics ("not yet implemented") — CLI deliberately doesn't
  implement flag reading; must hand-craft the field-4 message.

## Exploitation

Naive empty `ReadFlag` submessage (`22 00`) → rejected: `Bad encoding error`.
Root cause: server rejects any field encoded in canonical/default form (explicit
empty submessage, explicit varint 0) — a proper encoder would omit it. Fix: pad
field 4 with non-empty junk content, e.g. `22 02 08 01` (fake inner varint field).
Server does not semantically validate the inner bytes — presence/non-defaultness
is enough.

## Flag

`bushbashctf{n0w_d0_t5e_oth4r_tw0}`

Response also states: "You should submit this flag to the first mystery-server
challenge" — confirms a chained "mystery server II" exists, likely unlocked via
the unused field-5 `ReadMultipleMessages` variant.

Series: mystery server I → II. Field 5 (`ReadMultipleMessages`) not implemented by
this client CLI at all — strong signal it's the entry point for part II.
